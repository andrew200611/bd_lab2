# Лабораторна робота 2 · NoSQL

Предметна область — фріланс-платформа з лабораторної 1 (PostgreSQL, `freelancer_platform`).
Фрагмент «Картка замовлення» винесено в документну БД, реалізовано також у SQL,
поміряно швидкодію; окремо показано другий тип NoSQL. 

Середовище: Python 3.13 + `psycopg`, `pymongo`, `redis`; PostgreSQL 18,
MongoDB 8, Redis 8 на `127.0.0.1` (5432 / 27017 / 6379).
Пароль PostgreSQL задається змінною `FP_DB_PASSWORD` — у коді його немає

```bash
pip install "psycopg[binary]" pymongo redis
export FP_DB_PASSWORD=ВАШ_ПАРОЛЬ       # PowerShell: $env:FP_DB_PASSWORD="ВАШ_ПАРОЛЬ"
python bench/seed.py --scale 100000     # схема lab2, дані, проєкція в MongoDB
python bench/run.py --scale 100000 --reps 30 --concurrency 1  --out bench/results.csv
python bench/run.py --scale 100000 --reps 30 --concurrency 10 --out bench/results.csv
python mongo/project_cards.py demo      # базові CRUD + агрегація
python redis/basics.py                 # базові запити ключ-значення
```

## 1. Види NoSQL баз

| Тип | Модель | Доцільно для |
|---|---|---|
| Документна | BSON-документ, вкладені структури | Об'єкт цілком за одне читання → обрано для п. 3 |
| Ключ–значення | ключ → значення, TTL, `INCR` | Сесії, кеші, лічильники, ліміти → обрано для п. 6 |
| Широкостовпцева | ключ розділу + ключі сортування | Часові ряди, лінійний масштаб запису |
| Графова | вершини + ребра | Обходи зв'язків, рекомендації |



## 2. Чи ефективніше винести частину даних

Так — але тільки читальну проєкцію, не всю базу. Стрічка замовлень є 90% трафіку,
і в SQL кожен її виклик збирає 4 JOIN + підзапит кількості відгуків. Документ зберігає
картку вже зібраною. Натомість гроші, контракти й статуси лишаються в PostgreSQL:
їм потрібні транзакції. Ціна виносу — дублювання, синхронізація (outbox/change trail)
і дорожчий запис. Проєкція похідна й відновлювана: її втрата не втрачає жодного факту.

## 3. Винесення в MongoDB + розширення вимог

Нові вимоги до застосунку, які роблять NoSQL доцільним: (а) головна сторінка віддає
20 готових карток за `status + категорія + бюджет` без JOIN на запит; (б) `skills[]` —
пошук за навичкою; (в) різнорідні `attrs` за категорією (`stack/repo`, `formats`,
`languagePair`)

Шість таблиць лабораторної 1 → один документ `project_cards`:
`project` + `client` + `currency` + `category` + `stats.proposals` + `skills/attrs`.
Відгуки — окрема колекція `proposals`.
Є `$jsonSchema`-валідатори, `schemaVersion`, 4 індекси під Q1–Q5, і демо `insertOne / find / $inc / $group / deleteOne`.



## 4. Те саме в SQL

Схема `lab2`: 5 таблиць, `skills text[]`, `attrs jsonb`, індекси під ті самі запити.
- `lab2.v_project_card` — звичайне подання з `jsonb_build_object(...)`
- `lab2.mv_project_card` — контроль: денормалізоване матеріалізоване подання
  з тими самими індексами.

→ `sql/fragment.sql`

## 5. Тестування швидкодії

Метод: Q1–Q5 = реальні шляхи фрагмента (картка за id, стрічка, пошук за навичкою,
агрегат, додати відгук). Масштаби 1 000 / 20 000 / 100 000 (100× зростання), 5 прогрівів
+ 30 повторів, `concurrency = 1` і `10`. 

p50, мс · 100 000 замовлень · конкуренція 1

| Запит | PostgreSQL `view` | PostgreSQL `mv` | MongoDB |
|---|---:|---:|---:|
| Q1 картка за id | 0.833 | 0.432 | 1.233 |
| Q2 стрічка замовлень | 89.604 | 0.595 | 2.546 |
| Q3 пошук за навичкою | 64.537 | 120.080 | 22.314 |
| Q4 агрегат по категоріях | 72.398 | 113.659 | 189.232 |
| Q5 додати відгук | 2.341 | — | 4.428 |

Q2 при зростанні 1k → 100k: `view` 1.33 → 89.6 мс, MongoDB 1.91 → 2.55 мс.
Під `c=10`: 318.7 / 1.3 / 10.9 мс відповідно.


Висновок: виграє денормалізація, а не двигун — `mv_project_card` (0.595 мс)
швидший за MongoDB. Але MV треба повністю `REFRESH`, а документ оновлюється
інкрементально; SQL кращий на агрегаті Q4 і записі Q5. Отже, правильний підхід це — polyglot persistence:
кожне сховище під свою задачу. Повні дані → `bench/results.csv`.


## 6. Інший тип NoSQL — Redis

`SET/GET EX` (сесія з TTL), `HSET/HGETALL` (чернетка відгуку), `INCR/INCRBY`
(перегляди, атомарно), `ZADD/ZINCRBY/ZRANGE` (рейтинг), `INCR + EXPIRE`
(ліміт 10 запитів/хв). Усі ключі — похідні й відновлювані з PostgreSQL.

→ `redis/basics.py`
